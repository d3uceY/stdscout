# Wails v3 + Elm

How StdScout is wired, what each piece needs to work, and the recipe for
starting another app the same way.

Four languages, one job each: Go owns the machine, Wails v3 owns the window and
the build, Elm owns the DOM, and ~150 lines of JavaScript translate between the
two sides.

```
┌──────────────────────────────────────────────────────────────┐
│ Go  backend/*.go          PATH scan, file manager, models    │
│        ↕  (registered as a Wails service; exported methods   │
│            become JS bindings with a numeric call ID)        │
│ Wails v3  main.go         window, embedded assets, packaging │
│        ↕  (JSON over the webview bridge, one Promise each)   │
│ JS        frontend/src/main.js    ports → bindings → ports   │
│        ↕  (Elm ports: records only, never class instances)   │
│ Elm       frontend/elm/src/*.elm  state, view, subscriptions │
└──────────────────────────────────────────────────────────────┘
```

## Where everything is

```
main.go                          application.New, service registration, embed, window
go.mod                           module path — bindings paths derive from it

backend/
  binaries.go                    Binaries service: List() / Reveal() / Version()
  locations.go                   Locations(): PATH folders grouped, labelled, brand-marked
  scan.go                        the walk: PATH + PATHEXT, shadowed/system flags
  binaries_test.go, scan_test.go tests that do not need Wails at all

frontend/
  index.html                     loads /elm.js as a CLASSIC script, then /src/main.js as a module
  package.json                   elm make + vite scripts; gsap and @wailsio/runtime deps
  vite.config.js                 dev server on 127.0.0.1:9245 + the wails typed-events plugin
  elm.json                       elm-version 0.19.3, source-directories ["elm/src"]
  elm/src/Main.elm               port module: ports, Model/Msg, update, subscriptions, program
  elm/src/Types.elm              records, Msg, pure queries over the model
  elm/src/View.elm               all Html
  src/main.js                    the only file that knows both worlds
  src/sprite.js                  sprite-strip player (brand idle + easter eggs)
  public/elm.js                  BUILD OUTPUT of elm make, gitignored
  public/style.css               the entire design system
  public/brand/                  idle.png strip + clips/<name>-sheet.{png,json}
  bindings/                      GENERATED by wails3; never edit, regenerated -clean
  dist/                          BUILD OUTPUT of vite, embedded into the binary

build/
  config.yml                     app metadata + `wails3 dev` orchestration
  Taskfile.yml                   common tasks: frontend build, bindings, icons, dev server
  windows|darwin|linux/          per-platform build/package tasks
  appicon.png                    source for icon.ico / icons.icns
Taskfile.yml                     build | run | dev | package, dispatched by GOOS
```

Rule of thumb: `frontend/public/` is copied verbatim, `frontend/dist/` is
compiled and embedded, `frontend/bindings/` is generated, `frontend/elm-stuff/`
is a compiler cache. Only `elm/src`, `src`, `public/brand`, `public/style.css`
and `index.html` are hand-written frontend files.

## The data path, end to end

1. Elm's `init` returns commands that send two port messages:
   `request { action = "list", target = "" }` and the same for `"locations"`.
2. The `request` port hands the payload to `main.js` while `update` is still
   running — **before** Elm has patched the DOM.
3. `main.js` looks the action up in a map, calls the generated binding
   (`Binaries.List()`), which posts to Go by numeric call ID and returns a
   Promise.
4. Go runs, returns a slice of structs; Wails marshals it; `models.js` wraps
   each element in a generated class.
5. `main.js` strips those to plain objects (`{ name, path, logo, shadowed,
   system }`) and sends them back through `binariesFromJs`.
6. Elm's subscription turns that into `GotBinaries`, `update` stores it, `view`
   re-renders.
7. A `requestAnimationFrame` later, `main.js` runs the GSAP fade on the nodes
   that now exist.

Errors take the same road: anything thrown in a handler is turned into a string
and sent through `errorFromJs`, so Elm only ever models success or failure —
it never knows a Promise exists.

## What each layer needs to work

### Go / main.go

```go
//go:embed all:frontend/dist
var assets embed.FS
```

- The embed directive is resolved at **compile time**: `frontend/dist` must
  exist, so `npm run build` has to run before `go build`. The `all:` prefix is
  what lets the pattern match files starting with `.` or `_`, which Go skips by
  default.
- `application.NewService(&backend.Binaries{})` in `Options.Services` is what
  makes the bindings callable. Nothing else registers methods.
- Every **exported method** on the service becomes a binding. `(T, error)`
  becomes a Promise that rejects; a method with only `error` returns `void`.
- Services find the running app through `application.Get()` — no app pointer
  needs to be threaded into a constructor:
  `application.Get().Env.OpenFileManager(path, true)`.
- Window size lives here (`Width`, `Height`, `BackgroundColour`, `URL: "/"`).
  A 620x620 window gives a **604px client area** — that is what media queries
  actually see.

### Bindings

- `wails3 generate bindings -clean=true -time-type=Date` writes
  `frontend/bindings/<go module path>/<package>/`. With
  `module github.com/d3uceY/stdscout` the import is
  `frontend/bindings/github.com/d3uceY/stdscout/backend`.
- Each method gets a stable numeric ID (`$Call.ByID(2218778267)`, a hash of the
  qualified name). Rename or re-sign a Go method and the old ID stops matching —
  regenerate or the call fails at runtime, not at build time.
- Generated files are throwaway. Edit them and the next `-clean` run eats it.

### Elm

- `port module Main exposing (main)` — the `port module` keyword is what permits
  ports, and ports must be declared in the module that declares `main`.
- Port payloads are **plain JSON only**: numbers, strings, booleans, lists,
  records of those. No custom types, no `Maybe`, no class instances. Flatten in
  `main.js`; rebuild the shape in `update`.
- Outgoing ports are `Cmd msg`; incoming ports are subscriptions
  (`Sub.batch [ binariesFromJs GotBinaries, … ]`). Both must appear in the
  program's `subscriptions`/returned commands or nothing arrives.
- Compile with `elm make elm/src/Main.elm --output=public/elm.js --optimize`.
  That is a **classic script** that assigns `window.Elm`; load it with
  `<script src="/elm.js">` **before** the module script. Importing it as an ES
  module leaves `this` undefined and the app never mounts.
- `index.html` in this repo is static — Vite serves it from the root and the
  Elm build output is fetched as a plain file, not bundled.
- Elm renders before the DOM patch, so any GSAP work on freshly rendered nodes
  must wait one `requestAnimationFrame`.

### Vite

```js
export default defineConfig({
  server: { host: "127.0.0.1", port: 9245, strictPort: true },
  plugins: [wails("./bindings")],
});
```

- `plugins: [wails("./bindings")]` injects the generated
  `bindings/github.com/wailsapp/wails/v3/internal/eventcreate` module into the
  runtime's events module, which is what makes typed custom events work. It
  **errors at build time if bindings are missing** — so generation is a
  prerequisite of `vite build`, not an optional step.
- `9245` must match `VITE_PORT` in `Taskfile.yml`, which becomes the
  `-port` flag of `wails3 dev`.

### Task orchestration

- `task dev` → `wails3 dev -config ./build/config.yml -port 9245`.
  `build/config.yml` then runs three things: a blocking `wails3 build DEV=true`
  (compiles Elm + vite build into `dist`), a background
  `wails3 task common:dev:frontend` (the Vite server), and finally
  `wails3 task run`, which opens the dev-server URL with HMR.
- `dev_mode.ignore.dir` excludes `frontend`, so only `*.go` changes restart the
  app; frontend edits hot-reload through Vite.
- `common:build:frontend` depends on `generate:bindings` and `run: once` — the
  darwin universal build invokes it from two parallel arch builds, and without
  `once` the two `-clean` generations race the bundler
  (`Could not resolve "./bindings/<pkg>"`).
- `build:frontend` picks `build:dev` or `build` from `DEV`, so a dev build is
  unminified and a production build is minified.

### The sprite player (brand idle + easter eggs)

`public/brand/idle.png` is a 6-frame 32x32 strip driven by a clip literal in
`main.js`. The five reaction sheets are 34x34 cells around a 32x32 canvas
because they were exported from Aseprite with a 1px border.

`clipFromAseprite(json, src)` in `src/sprite.js` reads the export instead of
copying numbers:

| JSON field         | Becomes                          | Meaning                          |
| ------------------ | -------------------------------- | -------------------------------- |
| `sourceSize`       | `frameWidth` / `frameHeight`     | the canvas — this is what scales |
| `frame`            | `cellWidth` / `cellHeight`       | the packed cell — this is the step |
| `spriteSourceSize` | `padX` / `padY` when `trimmed`   | the border inside the cell       |
| `duration` per frame | `frameMsByFrame`               | one hold time per frame          |

`playSprite` measures the host box (`38x38`, `.brand-logo`) and derives one
scale from the **canvas** — `min(boxWidth / frameWidth, boxHeight / frameHeight)`
so a frame can never spill out of an oddly shaped box. The strip is then
`frames * cellWidth * scale` wide, and each frame translates by
`(frame - 1) * cellWidth + padX`. Scaling by the cell instead is how a padded
sheet ends up drawing 32/34 = 94% of the size of an unpadded one in the same
box. Do not "fix" that by editing the PNGs — the JSON already carries the
geometry.

Also worth keeping: `loop: false` clips resolve their promise on the last frame
(that is how a one-shot reaction hands the box back to the idle loop),
`stopSprite` replaces whatever is mounted, and reduced motion freezes on frame
one instead of animating.

## Starting another app

```powershell
# 1. Scaffold. `wails3 init` always creates <dir>/<name>, even with -d .
wails3 init -n myapp -t vanilla -d $env:TEMP\scaffold
Copy-Item $env:TEMP\scaffold\myapp\* . -Recurse -Force     # keep the repo root flat

# 2. Go side
#    write backend/<service>.go, register it in main.go, set Name/Title/size

# 3. Bindings
wails3 generate bindings -clean=true -time-type=Date
#    (never pass -f '' on PowerShell: the empty string swallows the next flag)

# 4. Elm
cd frontend
elm init                       # then set source-directories to ["elm/src"], versions to 0.19.3
```

Then make these five files agree with each other:

| File                | Must contain                                                    |
| ------------------- | --------------------------------------------------------------- |
| `frontend/elm.json` | `elm-version: 0.19.3`, `elm/html 1.0.1`, `elm/virtual-dom 1.0.5`, `elm/json 1.1.4` |
| `frontend/package.json` | `"type": "module"`, scripts `elm:build`, `build`, `dev`, and `gsap` + `@wailsio/runtime` |
| `frontend/index.html` | `/style.css`, `#app`, `<script src="/elm.js">`, `<script type="module" src="/src/main.js">` |
| `frontend/vite.config.js` | port `9245`, `plugins: [wails("./bindings")]`                |
| `frontend/src/main.js`  | `window.Elm.Main.init({ node, flags: null })`, then `app.ports.*` wiring |

Scripts that do the right order:

```json
"elm:build": "elm make elm/src/Main.elm --output=public/elm.js --optimize",
"elm:build:dev": "elm make elm/src/Main.elm --output=public/elm.js",
"dev": "npm run elm:build:dev && vite",
"build": "npm run elm:build && vite build --mode production",
"build:dev": "npm run elm:build:dev && vite build --minify false --mode development"
```

Full loop:

```powershell
cd frontend; npm install
npm run build              # elm make → public/elm.js, vite → dist/
cd ..; go build -o bin/myapp.exe .   # embeds dist/
# or, for the inner loop with HMR:
task dev                   # wails3 dev
```

## Things that cost time the first time

- **`elm make` output must be a classic script.** A `<script>` tag before the
  module, not `import`.
- **Elm compiles before Vite runs.** `public/elm.js` is gitignored, so always
  build through the npm scripts, never `vite` alone.
- **Regenerate bindings after touching Go.** The call ID is a hash; a stale
  binding fails at runtime with a confusing "unknown method".
- **Ports carry plain data.** Spreading a generated model class into a port
  message throws — map the fields explicitly.
- **Breakpoints below 620px.** The window is 620 wide but the client is 604, so
  a `max-width: 620px` query always fires.
- **Elm's root needs `flex: 1; min-height: 0`** or the page scrolls instead of
  the list.
- **`wails3 build` can exit 1 on Windows** because its Taskfile probes `uname`
  and `tail`; the binary is still produced.
- **Kill the running exe before `go build`** or the linker fails on a locked
  file.
- **GSAP and Elm's DOM patch disagree** for exactly one frame — defer one
  `requestAnimationFrame`, and check `prefers-reduced-motion` inside the
  animation call rather than at module top level.
- **Browser preview has no backend.** `Binaries.List()` rejects with a bare
  object, which is why `describe(err)` exists; UI work is still fully testable
  at `127.0.0.1:9245`.
